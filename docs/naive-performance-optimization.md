# Naive Outbound 性能优化方案

## 问题分析

### 当前性能问题
根据日志对比分析（0001.log vs 0002.log），发现以下关键差异：

1. **冷启动延迟**：首次建立连接需要 1.75-1.84 秒
2. **连接建立方式**：所有请求通过单一 HTTP/2 长连接复用
3. **连接中断频繁**：17秒时大量连接出现 "stream failed: aborted" 错误

### 根本原因
本项目使用 cronet-go 实现的 Native Naive 协议存在以下架构特点：
- 使用 HTTP/2 作为传输协议
- 所有流量通过单一长连接（或少数连接）复用
- 初始连接需要完整的 TLS + HTTP/2 握手过程

原版使用 libnaive 插件模式：
- 独立进程通过 SOCKS5 接口提供服务
- 连接管理由 C++ 原生库优化
- 无明显冷启动延迟

## 优化策略

### 1. 连接预热机制
**目标**: 减少首次请求的延迟

**实施方案**:
- 在 Outbound.Start() 阶段预建立连接到代理服务器
- 实现连接池预热，保持 1-2 个活跃的 HTTP/2 连接
- 使用 dummy request 激活连接（如 HEAD 请求）

**预期效果**: 将首次请求延迟从 1.8s 降低到 <500ms

### 2. 连接保活优化
**目标**: 减少连接中断导致的重连

**实施方案**:
- 调整 HTTP/2 PING 间隔，更主动地保持连接活跃
- 实现连接健康检查机制
- 在连接即将超时前主动发送保活数据

**预期效果**: 减少 "stream failed: aborted" 错误

### 3. 并发连接策略
**目标**: 提高并发性能

**实施方案**:
- 考虑使用多个 HTTP/2 连接代替单一连接
- 根据负载动态调整连接池大小
- 实现连接负载均衡

**预期效果**: 改善高并发场景下的性能

### 4. 快速失败与重试
**目标**: 减少连接故障对用户的影响

**实施方案**:
- 实现快速失败检测（< 100ms）
- 自动重试机制，透明地切换到备用连接
- 连接状态监控和自动修复

**预期效果**: 提高连接可靠性

## 实施计划

### Phase 1: 连接预热（优先级：高）
1. 修改 `outbound.go` 的 `Start()` 方法
2. 实现预连接逻辑
3. 测试验证冷启动性能改善

### Phase 2: 连接保活（优先级：高）
1. 研究 cronet-go 的连接配置选项
2. 调整 HTTP/2 PING 参数
3. 实现连接健康检查

### Phase 3: 高级优化（优先级：中）
1. 连接池管理优化
2. 并发连接策略
3. 性能监控和日志

## 技术限制

由于使用 cronet-go（基于 Chromium 网络栈），部分底层优化受限于：
1. cronet 引擎的配置选项
2. HTTP/2 协议本身的特性
3. 与原版 libnaive 在架构上的本质差异

某些场景下（特别是首次连接），可能无法完全达到原版性能，这是架构设计的权衡。

## 测试方法

### 性能指标
1. **冷启动延迟**: 从连接建立到首次响应的时间
2. **稳定性**: 连接中断率
3. **并发性能**: 多个并发请求的吞吐量
4. **资源占用**: CPU 和内存使用

### 测试场景
1. 首次访问网站（如 x.com）
2. 连续访问多个网站
3. 长时间保持连接（30分钟+）
4. 高并发请求（10+ 并发连接）
